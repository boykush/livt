livt は、オンラインホワイトボード（Miro や FigJam など）でチームが決めたことを、実例マッピングの形のままリポジトリに残し、チームの全職能の持ち物にするツールです。AI エージェントはそれを読み、BDD が目指してきた発見・定式化・自動化の流れを最後までたどれます。

AI 時代の BDD

BDD コミュニティは、発見が定式化より、定式化が自動化より大事だと言ってきました。合意した仕様は1つの一貫した形で持ち続ける、というのもコミュニティの考えです。

ただ、実例マッピングは会話の場で終わりません。ルールの変更も疑問点の解消も、開発のあいだ続きます。定式化した feature file だけでは、その移り変わりを追いきれません。livt は実例マッピングそのものを形式にして記録し、feature file に当たる内容を含んだまま、疑問点の解消やルールの変更まで、デザイナーやプロダクトマネージャー（PdM）を含む全職能で追えるようにします。

AI エージェントの進化で、状況が変わりました。合意したルールの自動化は、エージェントに任せられます。テストピラミッドに沿って自動化すると、実例マッピングのルールや具体例が、別々のレイヤや言語のテストで自動化されます。livt は、そのための型とツールを CLI と AI プラグインとして渡し、レイヤや言語の違いから来る課題を、エージェントと一緒に解きます。仕様を実行して検証したいチームには、Cucumber があります。

課題

  • 実例マッピングのその後は、定式化したファイル（feature file）だけでは追いきれない
  • Gherkin を実行できる仕様に保つには、ステップ定義を人が書いて保守し続ける必要がある
  • テストピラミッドに沿った自動化は層やリポジトリをまたいで散らばり、どのルールがどこで自動化されたかを追いづらい

顧客とユーザー

  • BDD を実践したいチームの全職能：プロダクトマネージャー（PdM）、デザイナー、開発者、テスターなど
  • AI エージェントに実装を任せているエンジニア

現在の解決手段

  • ルールと具体例を Gherkin に定式化してバージョン管理し、Cucumber で実行できる仕様として自動化する
  • 合意をチケットに書き写し、そこから先は同期しない

解決策のアイデア

  • 実例マッピングそのものを形式にして記録し、feature file に当たる内容を含んだまま全職能の持ち物にする
  • 実例マッピングはテキストとしてリポジトリに残し、変更は1つずつコミットとして積む。ルールの変更も疑問点の解消も、全員が差分で読める
  • 合意したルールの自動化は、AI エージェントに任せる
  • ルールと具体例には URI があり、テストは自動化した対象の URI を引用する
  • テストはどの層・どのリポジトリ・どの言語にあってもよい。livt が引用を集めて、ルールごとにどのテストが引用しているかを示し、テストが通ったかどうかはテストのレポートに任せる
  • 発見から定式化、自動化までの流れを、CLI と AI プラグインとして配る

ユーザーは価値を得るために何をするか

  • 合意したルールを AI エージェントに渡し、合う層のテストとして自動化させる
  • まだ自動化されていないルールを見て、次に埋めるものを選ぶ
  • 疑問点の解消やルールの変更を、職能を問わず同じ場所で追う

課題ごとのオポチュニティ

これらの課題は、livt 自身のリポジトリにオポチュニティとして1つずつ記録されています。それぞれにキャンバスとストーリーマップがあり、ライブデモで読めます。

追加 自動化 livt://ubiquitous/automation
+自動化
+実装リポジトリのテストがルールや具体例をlivt URIで引用し、その振る舞いを実行できる仕様として確かめること。テストのコメントに `livt:automates` とlivt URIを並べて書く。
+BDD の Automation にあたる。livtが知るのは引用があるかどうかで、テストが通ったかではない。ルールと具体例はそれぞれ自分への引用で自動化され、一方が他方を兼ねない。
追加 文脈 livt://ubiquitous/context
+文脈
+その用語の意味が通じる範囲。DDDの境界づけられたコンテキストにあたる。
+livt では `ubiquitous/{ctx}/` のディレクトリとして切り、同じ言葉が範囲ごとに違う意味を持つことを表す。
+文脈を切らない用語は、範囲を跨いで共通の意味を指す。

追加 実例マッピング livt://ubiquitous/example-mapping
+実例マッピング
+1つのストーリーについて、ルール・具体例・疑問点を色分け付箋で整理する手法。
+詳細ディスカバリーで仕様を具体化するために使う。
追加 定式化 livt://ubiquitous/formulation
+定式化
+記録した素のマッピングを、ルールは言い切りに、具体例はその名前だけで何の話か分かる形にして、チームの誰が読んでも同じ振る舞いを思い浮かべられる文書に整える工程。実装は見ず、変えてよいのは表現と構造だけで、その差分がレビューの対象になる。
+BDD の Formulation にあたり、Gherkin を書く行為に相当するのが実例マッピングの書き換え。Gherkin はそこから起こす生成物で、正となるのはマッピングのほう。
追加 実装リポジトリ livt://ubiquitous/implementation-repository
+実装リポジトリ
+livtリポジトリのルールを、自プロダクトのテストとして自動化する側のリポジトリ。ストーリーの `repos:` で宣言する。
+外へ渡るのはIssueとlivt URIというポインタだけで、戻るのはテストが何を自動化しているかの引用。コードを読むのは実装リポジトリの中で走る走査であって、livtリポジトリのビルドはその結果しか読まない。
+livtリポジトリと同一のリポジトリでも成立するが、それは両者が別々であるという一般形の特殊ケース。本リポジトリ自身がその特殊ケースにあたるため、同一である前提が暗黙に紛れ込みやすい。
追加 livtリポジトリ livt://ubiquitous/livt-repository
+livtリポジトリ
+ディスカバリーで合意し記録した成果物（ストーリー・ユーザーストーリーマップ・実例マッピング・ユビキタス言語）を収める置き場で、全ての機能開発の起点。
+サイト・CLI・MCPの出力はすべてここからの導出物。livt URIはこの中の一点を指し、ルート（`--root` / `LIVT_ROOT`）は各環境における所在を指す。
追加 livt URI livt://ubiquitous/livt-uri
+livt URI
+livtリポジトリの一点（オポチュニティ・オポチュニティキャンバス・ユーザーストーリーマップ・ストーリー・実例マッピング・ルール・具体例・疑問点・用語）を指す安定した名前。
+`livt://` で始まり、MCP・CLI・SSGが同じ形を使う。デプロイ先のURLには依存しない。

+オポチュニティ

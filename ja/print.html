livt - Living Text

livt - Living Text

Collaborate on board. Make it living in text.

何を作るかをボードを囲んで決めるチーム（たとえば実例マッピングで）は、合意を手にして部屋を出る。livt はその合意をリポジトリのテキストとして残し、それが生まれたボードの形で見せ、それを作る人とコーディングエージェントに届ける。livt が目指す成果はひとつ。協働の成果が、living text としてプロダクトとともに育っていくことだ。

なぜ livt があり、いつ向いているか

livt は自分の理由を、チームに理由を残してもらうのと同じやり方で残している。livt が立ち向かう課題はそのオポチュニティであり、チームがそれに対して livt で何をするかは、そのストーリーマップに描かれている。それらが記録であり、このページは、遅れをとりかねない写しを持つのではなく、それらを指し示す。

それらはライブデモにある。ライブデモは livt 自身の livtリポジトリで、変更のたびに livt build で再ビルドされる。デモは日本語で表示される。その理由は livt.yaml にある。

livt の境界

livt が何をほかに任せ、描いているプラクティスからどこで離れるかは、livt と BDD にまとめてある。使い始めるには README を参照。

livt と BDD

livt が描き出すのは、livt が発明したのではないプラクティスだ。このページでは、どこがコミュニティのもので、どこを livt が加え、どこで livt が意図して離れ、何に livt があえて手を出さないのかを述べる。

BDD コミュニティから来た人に手短に言えば、livt は Cucumber の代替ではない。テストは実行しない。発見のセッションで決めたことを残し、何か月も後に誰かがそれを実装するときにも、その決定を読めて、引用もできる状態に保つ。

livt が受け継いだもの

  • 振る舞い駆動開発（BDD） — Dan North、Introducing BDD（2006年）。livt が拠り所にしている3つのフェーズ、発見・定式化・自動化は、コミュニティ自身の枠組みだ。Cucumber の BDD ドキュメントを参照。
  • 実例マッピング — Matt Wynne、Introducing Example Mapping（2015年）。4種類のカードとその色、タイムボックス、そしてボードを読み返してストーリーについてのシグナルとして受け取ること。livt のボードはその形式を、ファイルから描いたものだ。
  • ユビキタス言語 — Eric Evans がドメイン駆動設計で用いた言葉で、BDD の定式化にも通じている。livt はそれを、使う側の成果物のそばに用語集として置く。
  • オポチュニティキャンバスとユーザーストーリーマッピング — Jeff Patton、Opportunity Canvas と story mapping。BDD ではないが、扱いは同じだ。

livt が加えたもの

以下はどれもプラクティスには含まれていない。livt のものであり、livt が変われば変わる：

  • 写真ではなくファイル。マッピングはリポジトリの中の YAML で、それが仕様を定めるコードと一緒にバージョン管理される。
  • 同一性。ルール・具体例・疑問点にはそれぞれ ID があり、一度付けたら変わらず、退役したものを飛ばして番号が振られ、livt URI で指せる。だから Issue やテストのコメントから引用したルールが、知らないうちに別の意味になることはない。
  • ライフサイクル。ルールはアーキテクチャ決定記録と同じように、提案され、合意され、却下され、あるいは退役する。退役したルールは、仕様の行き先を示す。
  • 非同期のレーン。わざわざ集まるまでもないルールなら、セッションの合間に、プルリクエストのレビューで提案して合意できる。
  • 外へのリンク。ルールは自身を自動化するために起票された Issue を記録し、それを自動化するテストは livt URI でそのルールを引用し返す。livt はその引用を実装リポジトリから集め（集めるのは各テストが何をカバーすると主張しているかであって、テストが通るかどうかではない）、サイトがそれを集計する。

livt が離れるところ

実例マッピングは使い捨てのはずのもの

これが本当の意味での逸脱であり、こっそり持ち込むのではなく、はっきり名指ししておく価値がある。

Wynne の実例マッピングは25分間の会話であり、その産物は共通理解だ。カードは副産物であり、計器でもある。青が多すぎればストーリーが大きすぎ、赤が多すぎればまだ準備ができていない。それを告げた時点で、カードは役目を終えている。ボードを写真に撮り、二度とその写真を開かないチームも、プラクティスに失敗したわけではない。

それでも livt がマップを残すのは、livt が埋めようとしているギャップのためだ。合意したルールを半年後に必要とする開発者は、写真に問い合わせることができない。とはいえ、残り続ける成果物は保守を招き、保守は、マップを交わすべき会話ではなく完成させるべき仕様として扱うことを招く。このアンチパターンは現実のもので、どんなツールもそれを排除できない。livt の構造上の答えは、記録は部屋が合意したあとに書かれ、合意した内容を決して変えないということだ。記録のスキルは、まずボードをそのまま書き写し、そのあとで初めて構造を整える編集を行う。レビューが読むのはその差分だ。

だからはっきり言っておく。どちらかを選ぶなら、会話を選ぶこと。よいセッションを開き、記録を何も残さないチームは BDD をやっている。完璧な YAML があってもセッションのないチームは、そうではない。

livt は定式化について、コミュニティと共有していない立場をとる

主流の BDD は、フィーチャーファイルを共有の成果物として扱う。Gherkin はスリーアミーゴスが一緒に生み出すものであり、それがリビングドキュメントになる。livt の立場はその逆をいく。発見の成果物が正であり、Gherkin はそこからの生成物になるはずのものだ。

それが今どれほどの意味を持つのかは、はっきりさせておく。livt は Gherkin をまったく生成しない。ツールのどこも、まだこの立場に依存していない。これは検証中の見解であり、livt の中で最も間違っている可能性が高い部分であって、リリースノートではなく議論の場に置かれるべきものだ。間違っていると思うなら、そう言ってほしい。同意よりもずっと役に立つ貢献になる。

livt がしないこと

  • テストの実行。livt は Cucumber、SpecFlow、Behave をはじめ、仕様を実行するどのツールの代替でもない。いつか Gherkin を出力することがあっても、それはそれらのツールが実行できる標準の構文であり、独自の方言には決してしない。
  • セッションのファシリテーション。タイマーも投票もボードもない。その場のファシリテーションは人が行い、その部屋がすでに使っているボードの上で進む。livt が始まるのは、ボードが終わるところからだ。
  • BDD を教えること。プラクティスは下に挙げる人たちが教えていて、そちらのほうがずっとうまく教えている。
  • コミュニティの言葉の再定義。ルール、具体例、疑問点、発見、定式化のようにプラクティスの用語であるものは、プラクティスでの意味のまま使う。livt が独自の用語を必要とした場合は、名前がそれを示している。livtリポジトリ、livt URI、実装リポジトリがそうだ。

これを書き残した人たち

livt が描くものの大半は、あるコミュニティが練り上げて公開してきたものだ。そのコミュニティは入門を無償で配り、踏み込んだ内容を販売していて、メンテナーは2023年から寄付で活動を続けている。

  • Dan North — Introducing BDD
  • Matt Wynne — Introducing Example Mapping
  • Seb Rose — Keep your scenarios BRIEF
  • Gáspár Nagy と Seb Rose — The BDD Books：Discovery と Formulation。Leanpub に日本語版がある
  • Cucumber School — 無料と有料のコース
  • Cucumber on Open Collective — メンテナーの活動資金の窓口

livt のおかげで、チームが一度済ませた議論をやり直さずに済んだのなら、その功績の一部は彼らのものだ。

リファレンス

このドキュメントはリファレンスを持たない。コマンドのリファレンス、ファイル形式ごとのガイド、MCP サーバーが返すものの表。どれも、ツールがすでに言っていることの2つめの写しになり、写しは誰かが更新を覚えていない限り古びる。それこそ livt が防ぐために存在する失敗なので、livt はリファレンスを同梱しない。

各詳細は一度だけ、それが記述するものからずれようのない場所、そしてそれを必要とする読み手（最近ではたいていコーディングエージェント）がすでに目を向ける場所に書かれている：

知りたいこと尋ねる先
コマンドが何を受け取るかlivt <command> --help
livtリポジトリの書き方：ファイル、その形式、変更するときのルールそれを書くスキル（plugins の下）
エージェントが livtリポジトリをどう読み、読んだものをどう引用するかlivtリポジトリに対して動かす livt mcp サーバー。自身のツールとリソースを自ら説明する
livtリポジトリの中の livt URI が何を指すかlivt resolve <uri>
livt 自身が何をするのか、そしてなぜなのかを、ルールごとにlivt 自身の livtリポジトリ：その実例マッピングで、ライブデモに描かれている

最後の行は、livt を livt 自身に使ったものだ。livt は自分のルールを livtリポジトリに置いているので、「livt は〜のときに何をするのか」という問いには、livt がどのチームに対しても答えるのと同じやり方で答えられる。合意されたルールと、それを合意したコミットにある理由によってだ。
